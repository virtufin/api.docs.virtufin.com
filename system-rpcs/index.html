    System RPCs

    The virtufin-api exposes a set of *System* RPC variants that are special-purpose, scope-narrowed entry points used by the platform's own services (WebSocketManager, WorkManager) for cross-service infrastructure data. The non-system variants remain the right choice for per-service private data.

    Pubsub system variants

    Pubsub.PublishSystemEvent(PublishSystemEventRequest)

    Publishes a CloudEvents v1.0 envelope to the fixed system-events topic. The topic field is intentionally absent from the request: clients cannot publish user-data events via this RPC.

    message PublishSystemEventRequest {
  bytes data = 1;
  map<string, string> metadata = 2;  // CloudEvents attributes, ce-* prefixed
}

    The metadata map SHOULD carry the standard CloudEvents v1.0 attributes (ce-id, ce-source, ce-type, ce-time, ce-specversion, ce-datacontenttype). The API uses these attributes as the published CloudEvent's envelope. The API fills in defaults for any missing attribute:

    Missing attribute Default
    ce-id Fresh GUID
    ce-source urn:virtufin.api
    ce-type com.virtufin.system.event
    ce-datacontenttype application/json
    ce-specversion 1.0

    The payload data carries the event-specific body (a JSON-encoded object whose shape depends on the publisher's ce-type).

    Pubsub.SubscribeSystemEvents(PubsubSubscribeSystemRequest)

    Server-streaming RPC. The client receives every event published to the system-events topic. Each event is delivered as a PubsubSubscribeResponse whose topic is system-events and whose metadata carries the CloudEvents attributes that the publisher set on PublishSystemEvent.

    Note: server-side type filtering is not yet supported. Subscribers receive every event. Filter client-side by metadata["ce-type"] and metadata["ce-source"].

    State system variants

    The state system variants operate against the configured StateServices.System service entry (services.json → name: "system", which maps to a Dapr state store). Callers never need to know which Dapr state store backs the system service; the API's ServicesConfiguration provides the mapping.

    State.SaveSystemState(SaveSystemStateRequest)

    Saves a key/value pair under the system service. Fires a state-changes event identical in shape to State.SaveState.

    State.GetSystemState(GetSystemStateRequest)

    Reads a single key. Throws NOT_FOUND if the key is absent.

    State.GetAllSystemState(GetAllSystemStateRequest)

    Returns all registered keys for the system service. Same semantics as State.GetAllState.

    State.RegisterSystemKeys(RegisterSystemKeysRequest)

    Registers keys for tracking by GetAllSystemState.

    State.DeleteSystemState(DeleteSystemStateRequest)

    Deletes a key. Fires a state-changes event.

    Rationale: why system variants?

    The system variants exist because:

    1. The service and topic namespaces are server-internal. Clients should not have to know that "the system events topic is called system-events" or that "the system state service is called system". These names are implementation details of the API.
    2. Type safety at the proto level. A caller that wants to publish a system event calls PublishSystemEvent, not PublishEvent(topic=...). The intent is clear in code and in generated stubs.
    3. Refactoring freedom. The API can change the underlying topic name or state service name without breaking clients.
